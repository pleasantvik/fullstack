## LinkedIn

I've started a five-month project to learn DevOps properly — not tutorials, an
actual application deployed to actual infrastructure, one new primitive a month.

Session one produced zero lines of application code.

What I did instead: initialised the repo, set up pnpm workspaces for the API and
the frontend, and pushed the first commit with branch protection on main.

Three things I didn't expect to learn from a scaffold:

**.gitignore only governs files git isn't already tracking.** Add a rule after a
file is committed and it does nothing — git keeps tracking it forever. That's
why the ignore rules went into the very first commit, before anything else, and
why I verified them with `git check-ignore` rather than assuming.

**Pattern order matters, and getting it wrong fails silently.** `.env.*` catches
every environment file; `!.env.example` rescues the one that should be shared.
Swap those two lines and .env.example quietly stops being committed. No error.
You find out when someone clones the repo and can't run it.

**The lockfile is committed, node_modules isn't.** Both are generated by the
same command. But the lockfile is the catalogue and node_modules is the
warehouse — you can rebuild the warehouse from the catalogue in seconds, and the
warehouse is full of platform-specific binaries that would break in a Linux
container anyway.

Branch protection on a solo project sounds like theatre. It isn't. In a few
weeks a merge to main will trigger a production deploy, and I want the pipeline
to be the only route there — including at 1am when I'm certain it's a tiny
change.

Next: Postgres in a container, Prisma schema, first migration.
